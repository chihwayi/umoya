# Avalon Gap-Closure Roadmap (S281+)

**Created:** 2026-10-24. Based on `AVALON_COMPETITIVE_ANALYSIS.md` (live walkthrough of https://hospital.avalonhealth.cloud/). Same discipline as the other roadmaps in this folder: every candidate gap was cross-checked against the actual codebase before being scheduled — nothing below is speculative.

## Method

1. Took the "Where Avalon is doing something genuinely worth noting" list from `AVALON_COMPETITIVE_ANALYSIS.md` as the candidate gap list.
2. Grepped the real codebase for each candidate before accepting it as a gap: medical-aid eligibility verification, referral management depth, WhatsApp integration, a global AI command palette, and interactive/visual education content.
3. Two candidates turned out to already be covered — documented below so they aren't re-investigated later. Three are real, confirmed gaps and get sprints. Two items from the analysis (self-serve tiered pricing UX, reseller/distributor program) are business/go-to-market decisions, not engineering gaps — flagged but deferred, not built speculatively.

## Part 1 — Findings (G1–G3)

| # | Finding | Evidence | Severity |
|---|---|---|---|
| G1 | **No real patient-facing WhatsApp channel.** Avalon advertises WhatsApp as a core, first-class patient-engagement pillar (reminders, messages) reachable from every patient's quick-actions. Umoya's only WhatsApp-adjacent code is a stray message-log entity and two DTO/provisioning references — no actual WhatsApp Business API controller, no outbound template-message service, no two-way inbox. (Umoya's separate Aurelia project does WhatsApp-native concierge work, but it is not wired into the core EHR's patient record — a doctor cannot message a patient on WhatsApp from inside a patient's chart today.) | `grep -rli whatsapp services/*/src`: only `at-message-log.entity.ts` (an SMS-gateway log, not WhatsApp), plus two unrelated DTO/provisioning string references. No `whatsapp.controller.ts` / `whatsapp.service.ts` anywhere in the monorepo. | HIGH — this is the single most visible, demo-able gap a private clinic evaluator would notice next to Avalon. |
| G2 | **No unified AI command palette.** Avalon's "Ask Avalon" (⌘K) is one interface combining navigation search, natural-language actions ("create an invoice for patient 30"), and clinical chat, with voice/hands-free modes, reachable from every screen. Umoya's CDSS guideline search is a strong, *grounded* clinical AI (unlike Avalon's — see the analysis doc) but it lives on a dedicated screen, not a global command surface, and there's no natural-language action execution ("book an appointment for X") anywhere in the frontend. | `grep -rli "command.*palette\|cmdk\|global.*search" ehr-frontend/src`: zero hits. | MEDIUM-HIGH — not a clinical-safety gap (Umoya's underlying AI is better), but a real UX/perceived-sophistication gap in a head-to-head demo. |
| G3 | **No interactive/visual content type in the patient-education LMS** (Avalon's "3D Anatomy" module, niche but distinctive). Umoya's `health-education.service.ts` / `patient-health-education.service.ts` already run a real, multi-language course→module→lesson LMS with enrollment tracking — structurally more capable than Avalon's module appears to be — but every lesson is `content_body` text/video only. No field for an embedded 3D model, interactive diagram, or annotated-image asset. | `grep -n "model_url\|3d\|interactive\|anatomy"` across both education services: zero hits. Lesson DTO only has `contentBody`/`contentType`/`durationMinutes`. | LOW — niche, nice-to-have, not a trust or clinical-safety issue. Scope small. |

## Part 2 — Sprint Plan (S281+)

| Sprint | Title | What It Delivers | DB provisioning touch? |
|---|---|---|---|
| **S281** ✅ | WhatsApp Patient Engagement Channel | **Implemented 2026-10-23.** Meta WhatsApp Cloud API integration under `services/ehr-service/src/whatsapp/` (HMAC-verified webhook, ported from the proven Aurelia project): `whatsapp-channel-config.entity.ts` (encrypted per-tenant credentials), `whatsapp-consent.entity.ts`, `meta-whatsapp.provider.ts`, `whatsapp-messaging.service.ts`, `whatsapp-webhook.controller.ts`. Webhook resolves tenant from `:tenantSlug` in the URL (Meta can't send `X-Tenant-ID`) — bypassed in `tenant.middleware.ts`'s `isPublicTenantEndpoint` allowlist, same pattern as the existing payment/Daily.co bypasses. `NotificationsService`'s three existing trigger methods (`sendAppointmentReminder`, `sendPrescriptionReady`, `sendLabResultsReady`) now also fire a best-effort, consent-gated WhatsApp send alongside the existing SMS, using PHI-minimizing generic bodies (no medication/test names in the WhatsApp copy). Two-way thread + opt-in toggle surfaced on the patient chart (`PatientDetail.tsx` → `WhatsappEngagementPanel.tsx`), reusing the existing `AtMessageLog`/`AtMessagingService` channel-log family (`channel: 'whatsapp'`) rather than new parallel tables. Channel credentials (`phone_number_id`/`access_token`/`app_secret`) are provisioned per-tenant via direct SQL insert at WhatsApp-onboarding time, matching the existing `SmsGatewayConfig` precedent (no admin CRUD UI exists for that either — not built speculatively). `tsc --noEmit` clean in `ehr-service`, `tenant-service`, and `ehr-frontend`. | Yes — `whatsapp_engagement` golden-rule provisioning bundle (`whatsapp_channel_configs`, `whatsapp_consents`) in `database-provisioning.service.ts` |
| **S282** | "Ask Umoya" — Unified AI Command Palette | A global ⌘K-style palette reachable from every screen: (1) navigation/action search (jump to a patient, open a module, "create an invoice for patient X"), (2) the *existing* grounded CDSS guideline search folded in as one of its modes rather than a separate screen — so the palette's clinical-question path still returns page-level citations, unlike Avalon's ungrounded equivalent. Voice input is a stretch goal, not required for v1 — ship the palette with grounded RAG search and basic action-routing first, since that alone matches Avalon's UX surface while keeping Umoya's actual safety advantage front and center. | No — frontend-only, plus wiring to existing `/api/cdss/guidelines/search` and existing REST endpoints for action execution |
| **S283** | Interactive Education Content | Extend the lesson content model with an optional `content_type: 'interactive'` / `asset_url` field, and add a lightweight embedded viewer (start with annotated-SVG/image-hotspot diagrams as the realistic MVP — a full 3D anatomy engine is a much bigger undertaking and not worth building from scratch; evaluate embedding an existing open-source anatomy viewer before building one). Scope modestly: this is a nice-to-have differentiator, not core clinical functionality. | Yes — additive columns on `education_lessons`, no new tables |
| **S284** *(deferred — business-contingent)* | Self-Serve Tiered AI Packaging | Only worth scheduling if Umoya ever pursues direct private-clinic/SMB self-serve sales the way Avalon does (Starter/Standard/Premium with AI features gated by tier). The underlying mechanism already exists — tenant `featureFlags` already supports fine-grained per-feature toggles (`advancedCDSS`, `patientPortal`, `telemedicine`, etc.) — so this sprint would be a thin self-serve pricing/upgrade UI and billing-flow layer on top of infrastructure that's already there, not a deep engineering gap. Do not build speculatively ahead of an actual go-to-market decision. | No — infrastructure already exists |
| — *(not a sprint — business decision)* | Reseller/Distributor Program | Avalon's 10–20% recurring-commission reseller channel is a go-to-market structure, not a product gap. No engineering work implied; flagging only so it's not forgotten if Umoya's commercial strategy ever needs a competitive answer. | n/a |

S281–S283 are real, verified, present-day gaps worth scheduling now — they're the specific things a side-by-side demo against Avalon would expose. S284 is flagged for awareness but intentionally deferred until a direct self-serve sales motion is an actual plan, not built ahead of need.

## Definition of Done

Same discipline as the other roadmaps in this folder: verify against real callers before claiming a fix, any DB schema change goes through `getProvisioningBundles()` per the golden rule, `tsc --noEmit` clean in every workspace touched, and don't build S284 speculatively — confirm the self-serve sales plan is real first. For S281 specifically: reuse Aurelia's proven WhatsApp Cloud API + HMAC verification code rather than re-implementing it, and keep clinical content out of WhatsApp message bodies (link to the portal instead) — this is both a PHI-safety practice and a point of genuine differentiation from what Avalon appears to do.
